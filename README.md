# Local Medallion Architecture and Analytics Dashboard

An end-to-end analytics solution over five Microsoft Fabric sample datasets,
built entirely locally with Python, SQLite and Streamlit. Bronze, Silver and
Gold layers are generated by reproducible scripts; no manual editing of the
database occurs at any point.

---

## The finding that shaped the architecture

**The source datasets do not join.** Profiling the raw files first, before
writing any transformation, showed that the intended foreign keys reconcile
on a fraction of a percent of rows:

| Relationship | Rows matched | Of | Rate |
|---|---|---|---|
| `sales.Order_ID` → `orders` | 42 | 31,115 | **0.13%** |
| `location.Order_ID` → `orders` | 43 | 25,504 | **0.17%** |
| `sales.Agent_ID` → `agent` | 481 | 31,115 | **1.55%** |
| `agent_commission.Agent_ID` → `agent` | 898 | 60,991 | **1.47%** |

A three-way join of sales, orders and location returns **zero rows**.
Whitespace, casing, and prefix distribution were all ruled out as causes; the
identifiers are structurally identical and semantically unrelated, i.e.
generated independently per file.

A conventional star schema on these keys would collapse to roughly forty
rows. The critical risk is that it collapses **silently** — a dashboard built
on that join would display precise, confident, entirely wrong numbers.

**What does conform is the descriptive layer.** Product category matches
exactly across `orders` and `agent_commission`; all 23 countries and all 76
cities are shared between `location` and `agent`; and every city resolves to
exactly one state, country and region. The data joins at the *dimension*
level even though it does not join at the *transaction key* level.

The architecture follows from that: each source is modelled as its own fact
table against conformed dimensions, and the integrity gap is measured and
published rather than hidden.

## Setup

Requires Python 3.11 or later. `sqlite3` is in the standard library.

```bash
pip install -r requirements.txt
```

Place the ten source CSV files in `data/raw/`. They are the Microsoft Fabric
Materialized Lake Views tutorial samples, named `{timestamp}-{dataset}.csv`,
two batch files per dataset for `agent`, `agent-commission`, `location`,
`orders` and `sales`.

## Running the pipeline

Run in order. Each stage reads only from the stage before it.

```bash
python src/profile_raw.py     # optional: reproduces the profiling findings
python src/load_bronze.py     # raw CSV  -> bronze_*
python src/build_silver.py    # bronze_* -> silver_*
python src/build_gold.py      # silver_* -> gold_*
streamlit run dashboard/app.py
```

Every stage is idempotent — tables are replaced, not appended — so the
database can be regenerated from scratch at any time by rerunning the three
build scripts. Delete `database/analytics.db` first if you want to prove it.

## The layers

### Bronze — faithful capture

Five tables, every column stored as text, nothing cleaned. Reading as text is
not incidental: 3,063 `Sales` values carry leading zeros that type inference
would strip, and because each dataset arrives as two files read separately,
pandas could infer different types per batch and silently produce a mixed
column after concatenation.

Three lineage columns are added per row — `source_file`, `source_row`,
`batch_timestamp` (parsed from the filename) and `ingested_at`. Once the
batches are concatenated, the filename is the only remaining record of which
batch a row came from, and two findings depend on it: all 137 agent ID
collisions span the two batches, and 88 of the 152 commission conflicts occur
*inside* one batch — which is what rules out resolving them by taking the
latest load.

The load asserts that the row count in the database matches an independent
count of the source files, read without pandas so the check is not comparing
pandas against itself.

### Silver — typing, grain, and quality

Types are cast explicitly, columns standardised, grain established per table,
and every table given a surrogate primary key.

**No row is ever deleted.** The duplicate keys in this source are collisions
between unrelated records, not redundant copies, so there is no basis for
choosing which row of a pair is correct — dropping either loses a real order
or a real agent. Rows coexist under a surrogate key and are labelled instead.

Quality is expressed two ways. Every row carries a `dq_status` of `valid`,
`warning` or `quarantine`, so downstream layers filter with one predicate.
Separately, `silver_data_quality_issues` holds one row per problem found,
keyed on the surrogate, so any flagged record can be joined back and
inspected.

The dividing line between the two grades is **whether the record can be
trusted, not whether its key is clean**. An ID collision leaves a complete,
internally consistent record with an ambiguous identifier — that is a
`warning`. Two commission rates for one agent and category means the measure
itself is contradictory — that is a `quarantine`.

Referential integrity is **measured, not enforced**. The function is named
accordingly. Enforcing it would quarantine 99.87% of sales.

### Gold — six marts, one per business process

There is no wide fact table. Each process is aggregated from the single
Silver table that holds its data, joined only to dimensions that conform.

| Mart | Grain | Source | Coverage |
|---|---|---|---|
| `gold_sales_summary` | priority × discount level | `silver_sales` | 99.13% |
| `gold_order_fulfilment` | month × category × ship mode | `silver_orders` | 100.00% |
| `gold_geography_segment` | region × country × state × city × segment | `silver_location` | 100.00% |
| `gold_agent_commission` | product category | `silver_agent_commission` | 99.50% |
| `gold_matched_sales_orders` | sales key × order line key | joined | **0.13%** |
| `gold_data_quality_summary` | business process | all | — |

The first four draw on essentially all of their source. The fifth is the only
one that joins two facts, and it is the only one that collapses. That
contrast is the argument for the whole design.

Each mart's declared grain is enforced as a unique index. These tables are
far too small for an index to matter for performance; the constraint exists
so the grain claim is testable rather than asserted in a comment.

## Grain and keys

No natural key in this source is unique. Every primary key is a surrogate.

| Table | Grain | Natural key | Failure |
|---|---|---|---|
| `silver_agent` | one agent | `agent_id` | 137 collisions, all cross-batch |
| `silver_agent_commission` | agent × category | `(agent_id, product_category)` | 152 conflicting rates |
| `silver_orders` | order line | `(order_id, order_date, product)` | 2 possible split shipments |
| `silver_sales` | one order | `order_id` | 23 collisions |
| `silver_location` | one order | `order_id` | 16 collisions |

Duplicate keys were diagnosed rather than assumed to be defects, by asking
whether the repeated rows agree on the attributes they would have to share if
they described the same entity. **Only `orders` came back saying the grain
assumption was wrong** — 15 of its 18 repeated IDs share an order date and
category and differ only in product, so those are line items and the grain is
finer than the table name implies. In the other four tables, no duplicate
pair shares a customer, a city, a name or a rate, so those are defects.

Six alternative composite keys were tested and rejected despite being unique:

| Rejected | Reason |
|---|---|
| `(order_id, shipping_date)` | mutable fact attribute, not identity |
| `(agent_id, city)`, `(agent_id, agent_name)` | attributes, not identity; only 400 distinct names |
| `(order_id, location_id)` | `location_id` references nothing — 330 values map to several cities |
| `(order_id, customer_id)` | violates `order_id → customer_id`; breaks 2NF |
| `(order_id, customer_name)` | same dependency problem; 400 names across 25,504 rows |

The last two matter most: an order has exactly one customer, so `order_id`
functionally determines `customer_id`. Those combinations are unique only
*because* 23 rows violate that dependency — using the defect to conceal the
defect.

## Assumptions

1. **The two batch files per dataset are incremental appends, not full
   snapshots.** Evidence: zero full-row duplicates across batches, and the 137
   agent collisions carry genuinely different data rather than two versions of
   one record. If they were snapshots, Silver would need to deduplicate to the
   latest batch per key instead of retaining both rows.

2. **Leading zeros in `Sales` are fixed-width padding, not meaning.** Verified
   rather than assumed: every value is exactly 8 characters, and zero-padding
   the cast integer back to 8 reproduces the source string on every row. Both
   checks are recorded in `silver_data_quality`.

3. **`Discount` (0–9) is carried through unscaled.** The source does not
   document whether it is a percentage, a decile or a band, so it is neither
   rescaled nor relabelled.

4. **Monetary values are treated as unscaled magnitudes.** `Sales` is a
   fixed-width 8-digit value with a median of 50.2 million against a maximum
   shipping cost of 999. Scale and currency are unknown, so figures are
   comparative only.

5. **ID collisions are retained, not resolved.** No evidence distinguishes the
   correct row of a colliding pair.

6. **The two remaining `orders` duplicates are possible split shipments** —
   same order, date and product with different ship modes ten days apart. Two
   cases is not enough evidence to change the grain declaration, so they are
   flagged rather than resolved.

## What cannot be answered, and why

| Question | Why not |
|---|---|
| Revenue over time | `sales` has no date column; joins to `orders` on 0.13% of rows |
| Revenue by product category | Category is in `orders`, revenue in `sales` |
| Revenue by region | Geography is in `location`, which joins to `sales` on 51 of 25,504 rows |
| Profit margin | `sales` and `profit` correlate at **−0.001** |
| Unit price | `sales` and `quantity` correlate at **0.005**; 271 rows have zero quantity |
| Customer-level analysis | 31,038 customer IDs across 31,115 rows; `customer_name` has 400 values drawn from the same pool as agent names |
| Commission by agent geography | Commission resolves to the agent master on 1.47% of rows |

Each absence is recorded with its cause in `gold_data_quality_summary` rather
than left as an unexplained gap.

## Signals that are not credible

Several figures are internally consistent but not plausible as business
reality, and would be raised with a stakeholder before any conclusion:

- **First Class and Standard Class have the same average delivery time**
  (15.5 days, across every category, across thirteen years). If that were
  real, nobody would pay for First Class.
- **Customer segments split 33.4 / 33.3 / 33.3.** No retailer has a perfectly
  uniform segment mix.
- **Commission runs uniformly from 1.00% to 99.99%,** with 6,205 agents above
  90%. A 99.99% commission is not a viable arrangement.
- **Every measure's median sits at the midpoint of its range** — the
  signature of uniform random generation.

## Analytical insights

**1. The integrity failure is upstream, not analytical.** The keys are
structurally valid and semantically unrelated, which points at independent
generation per file rather than a parsing or ETL fault at this end. The fix
belongs with the source system owners; nothing built downstream can recover
it.

**2. Three things a business can act on today.** Fulfilment volume and
delivery time by category and ship mode; order distribution across 23
countries and three customer segments; and commission cost by category. All
three cover 99–100% of their source tables.

**3. The cost of the gap is quantifiable and the fix is prioritisable.**
Repairing order ID generation would unlock the entire revenue analytics
surface — by category, by region, over time. Until then, anyone building a
category revenue report on this data is reporting on 42 orders without
knowing it. That is the finding to escalate first.

**4. Regional volume is misleading at face value.** Europe leads on delivery
records, but it holds 24 of the 76 cities; per city it is in line with every
other region. A raw regional bar chart would suggest a concentration that
does not exist.

## What I would improve in production

- **Staged writes.** Each layer currently replaces its tables in place. A
  production build would write to staging tables and swap them in only after
  every check passed, so a mid-run failure cannot leave a half-rebuilt
  warehouse. `pandas.to_sql` issues its own DDL, so the current rollback is
  best-effort.
- **Explicit DDL.** Tables are created by `to_sql`, which infers types.
  Declaring `CREATE TABLE` with types, `NOT NULL` and `CHECK` constraints
  would enforce at the schema level what is currently enforced in code.
  Surrogate keys and mart grains are covered by unique indexes as an interim.
- **Incremental loads.** The pipeline is a full refresh. Sequential surrogate
  keys are stable only for an unchanged dataset — new data arriving mid-sort
  would renumber existing rows. A production version would derive keys from a
  hash of the natural key plus batch, or inherit a stable Bronze row ID.
- **Quality thresholds and alerting.** The quality tables record results but
  nothing fails on a threshold. A production build would fail or alert when a
  match rate drops below an agreed floor.
- **Run history.** Each run overwrites the quality tables. Retaining a build
  audit log would let quality be trended rather than only observed.
